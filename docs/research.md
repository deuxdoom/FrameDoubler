## R10. 시작 시각과 장기 동기 (2026-11-13, P4-3)

- 원본 영상/오디오의 가장 이른 시작을 0으로 정규화합니다. 원시 영상의 fps는 `-framerate`로 지정하고 `-copyts`, 입력별 `-itsoffset`, `fps_mode=passthrough`를 사용합니다. 입력 `-r`과 CFR 재배치는 시작 오프셋을 없애므로 사용하지 않습니다. 고정 fps 원시 입력이므로 출력은 여전히 CFR입니다. [FFmpeg timestamp 옵션](https://ffmpeg.org/ffmpeg.html#Advanced-options).
- AAC 변환에서는 `aresample=async=1:first_pts=0`으로 늦게 시작하는 오디오 앞을 무음으로 채웁니다. 양의 시작 시각에서 AAC 인코더의 1024샘플 지연이 유효 오디오로 남는 문제를 피합니다. 일반 오디오 복사 경로는 상대 시작 오프셋을 보존합니다.
- `verify`는 모든 오디오 트랙의 디코딩된 프레임 PTS와 샘플 수를 유리수로 읽고 시작·25%·50%·75%·끝의 입력 대비 동기 변화와 유효 길이를 검사합니다. Matroska의 1ms 단위 패킷 duration을 합산하면 1024/48000초를 21ms로 잘라 누적 오차를 잘못 계산하므로 샘플 수를 사용합니다. 트랙 앞의 묵시적 무음과 AAC priming/padding을 반영합니다. 트랙 누락과 1프레임 초과 변화는 실패입니다. 타임스탬프를 유지한 채 소리 내용을 바꾸는 오류까지 검출하지는 않습니다.
- 검증: probe/encode/pipeline 64개, 짧은 동기 테스트 6개와 별도 장기 테스트 1개 통과. ±250ms 오프셋, VFR, 실제 파형의 소리 시작, 오디오 누락/100ms 지연을 검사했습니다. 600.6초 29.97fps 합성 입력을 36,000프레임 59.94fps로 변환하여 길이 차이 0ms, 다섯 지점 최대 0.33ms로 통과했습니다. 전체 정지 영상의 판정 준비 구간을 잔여 중복으로 오인하던 검증기도 수정했습니다.
- 실제 4K 샘플의 새 출력 `FireEmblem_sync_60fps.mp4`는 길이 차이 0ms, 다섯 지점 모두 -4.3ms로 통과합니다. 원본 오디오가 영상보다 52ms 짧은 점은 보존합니다. 원본부터 존재하는 음화 불일치의 수정은 이번 범위가 아닙니다.

## R2. 추론 속도와 VRAM (2026-11-13, P0-2)

환경: RTX 4080 SUPER, Python 3.14.7, PyTorch 2.14.1+cu130. 측정 스크립트는 `F:\Temp\FrameDoubler\spike\bench.py`이며, 프레임 한 쌍을 `time_step` 0.5로 보간하는 시간을 20회 평균했습니다. 디코딩과 인코딩 시간은 포함되지 않았습니다.

| 해상도 | scale | fp16 시간 | fp16 초당 보간 수 | fp16 VRAM | fp32 시간 | fp32 VRAM |
|---|---|---|---|---|---|---|
| 1920x1080 | 1.0 | 12.9 ms | 78 | 0.6 GB | 21.1 ms | 1.3 GB |
| 2560x1440 | 1.0 | 21.6 ms | 46 | 1.1 GB | 41.3 ms | 2.1 GB |
| 3840x2160 | 1.0 | 53.2 ms | 19 | 2.3 GB | 104.2 ms | 4.6 GB |
| 3840x2160 | 0.5 | 38.8 ms | 26 | 1.9 GB | 73.6 ms | 3.5 GB |

- v4.25와 v4.26의 속도는 같습니다.
- 30→60fps 변환에서는 영상 1초마다 보간이 30회 필요합니다. 따라서 추론만 계산하면 1080p는 실시간의 약 2.6배, 1440p는 약 1.5배, 4K는 약 0.63배(scale 0.5에서는 약 0.85배)의 속도입니다.
- fp16은 fp32보다 약 2배 빠르고 VRAM을 절반만 사용하므로 기본값으로 정합니다.
- `torch.backends.cudnn.benchmark = True`를 사용하면 새 해상도를 처음 처리할 때 알고리즘 탐색 때문에 VRAM 최대 사용량이 4K에서 9.4 GB까지 일시적으로 증가했습니다. 위 표의 VRAM 값은 탐색이 끝난 뒤의 값입니다. 이 옵션의 사용 여부는 P3-1에서 정합니다.
- 합성 프레임(움직이는 사각형)으로 확인한 결과, `time_step` 0.5의 출력이 두 프레임의 중간 위치와 일치했습니다.

## R3. 기술 스택 결정 (2026-11-13, P0-2)

- 언어는 Python, 추론은 PyTorch(CUDA)로 확정합니다. 공식 모델을 변환 없이 사용할 수 있고, 4K에서도 VRAM이 16 GB 안에 충분히 들어오며, 속도가 오프라인 변환 용도에 적합합니다.

- PyTorch의 CUDA 빌드는 `https://download.pytorch.org/whl/cu130` 색인에서 설치합니다.
- TensorRT와 ncnn Vulkan 백엔드는 조사하지 않았습니다. P6-1의 측정에서 추론이 병목으로 확인될 때에만 조사합니다.
- 이 PC에는 FFmpeg가 설치되어 있지 않습니다. 설치 방법과 빌드의 종류(LGPL 또는 GPL)는 P0-3과 P0-4에서 정합니다.

## R4. 참고 프로젝트에서 확인한 설계상의 교훈 (2026-11-13)

Video2X 6.4.0 이후 버전의 구조를 읽고 확인한 내용입니다. FrameDoubler의 설계에 반영할 사항만 기록합니다.

- 프레임을 디스크에 저장하는 방식은 용량과 입출력 때문에 느립니다. 프레임은 메모리 안에서만 전달합니다.
- 정수 배율로만 보간하고 중복 프레임을 판정하지 않으면, 30fps 내용이 담긴 60fps 파일에서 중복 프레임 사이를 보간하게 되어 결과가 개선되지 않습니다.
- 디코딩, 추론, 인코딩을 하나의 스레드에서 순차적으로 실행하면 GPU가 쉬는 시간이 발생합니다. 스레드 분리는 P6-2의 후보입니다.
- 프레임을 CPU에서 8비트 RGB로 변환하면 고해상도에서 비용이 크고 10비트 입력의 정밀도가 손실됩니다. 색 변환은 GPU에서 수행하는 방식을 우선 검토합니다.
- 프로세스 사이의 파이프로 원시 프레임을 주고받을 때 프레임 크기가 어긋나면 처리가 멈춥니다. 프레임 크기를 `probe`의 결과로 고정하고 정확한 바이트 수만큼 읽어야 합니다.

## R6. 중복 판정 지표 (2026-11-13, P2-1과 P2-2)

- 프레임 전체의 평균 차이는 움직임이 적은 구간에서 중복과 새 프레임이 겹칩니다(실제 샘플: 중복 최대 0.25, 새 프레임 최소 0.10).
- 16x16 블록별 최대 차이는 잘 분리됩니다(실제 샘플: 중복은 중앙값 0.23과 최대 0.81, 새 프레임은 최소 2.88과 중앙값 110). 따라서 판정에는 블록 차이를 사용합니다.
- 판정 규칙은 두 가지입니다. 첫째, 블록 차이가 이웃한 차이의 최댓값의 0.5배 이하이고 4.0 미만이면 중복입니다. 둘째, 블록 차이가 잡음 수준(최근에 확정된 중복 31개의 중앙값의 2.5배, 확정된 중복이 5개 미만일 때에는 0.5)보다 작으면 중복입니다. 둘째 규칙은 3회 이상 반복의 가운데 프레임과 정지 화면 구간을 처리합니다.
- 중복이 4회를 초과하여 이어지면 이후의 프레임은 정지 화면으로 분류하여 그대로 출력합니다. 긴 정지 뒤에 화면이 바뀔 때 두 화면 사이를 길게 보간하지 않도록 하기 위한 규칙입니다.
- 합성 영상에서는 프레임 번호 표시가 매 프레임 바뀌어 판정이 지나치게 쉬워지므로, 테스트에서는 `synth.strip_code`로 이 영역을 지운 뒤에 판정기에 전달합니다.

## R7. 모델 비교, 장면 전환 지표, 전체 처리 속도 (2026-11-13, Phase 3)

- 모델 비교: 실제 샘플의 고유 프레임 U[i]와 U[i+2]를 보간하여 U[i+1]과 비교했습니다(PSNR, 58개 평균). 4K에서 scale 0.5는 v4.25가 27.22 dB, v4.26이 27.21 dB이고, scale 1.0은 각각 26.03 dB와 26.12 dB입니다. 두 모델의 차이는 없고, 4K에서는 scale 0.5가 약 1 dB(움직이는 구간에서는 약 2 dB) 더 좋습니다. 기본 모델은 공식 권장값인 v4.25, scale은 세로 1440 초과에서 0.5로 정했습니다.
- 장면 전환: 화소 차이의 평균은 빠른 카메라 이동(실제 샘플 최대 30.9)과 장면 전환(합성 영상 24.5와 27.2)을 구분하지 못합니다. 4x4 격자별 휘도 히스토그램 거리의 평균은 빠른 카메라 이동이 최대 0.114, 장면 전환이 0.75 이상으로 분리됩니다. 임계값은 0.35입니다. 실제 게임 영상의 장면 전환으로는 아직 검증하지 못했습니다(P4-5).
- 전체 처리 속도: 실제 4K 샘플(478프레임)의 변환에 23.9초가 소요되었습니다(출력 20.0fps, 실시간의 0.33배). 추론만 측정한 값보다 느리므로 디코딩, 프레임 전달, 인코딩에 병목이 있습니다(P6-1).
- 출력 파일의 비트레이트는 `hevc_nvenc` 품질 19에서 약 32 Mbps입니다(입력은 H.264 약 61 Mbps).
- VFR 입력은 평균 프레임레이트가 아니라 컨테이너의 기준 프레임레이트(`r_frame_rate`)로 출력 fps를 정해야 합니다. 평균값을 사용하면 출력이 51.7fps처럼 어긋납니다.
- 16비트 프레임을 반정밀도로 변환할 때에는 float32에서 0과 1 사이로 나눈 뒤에 변환해야 합니다. 65535는 반정밀도의 표현 범위를 넘습니다.

## R8. 인코딩 옵션과 유튜브 업로드 프리셋 (2026-11-13, P4-1)

- 근거: [유튜브 권장 업로드 인코딩 설정](https://support.google.com/youtube/answer/1722171?hl=en). 실시간 방송용 설정이 아닌 업로드용 SDR 설정을 사용합니다. 권장은 MP4/Fast Start, H.264 High, 4:2:0, VBR, CABAC, B 프레임 2개와 약 0.5초의 closed GOP입니다.
- `youtube` 프리셋은 출력 해상도와 fps로 비트레이트를 정합니다. 아래 값 중 4K는 권장 범위의 상한을 선택했습니다. 영상 크기와 fps를 바꾸지는 않습니다. 59.94fps도 고프레임레이트 값으로 처리하며, 4K·60fps 초과는 프리셋 적용 오류로 안내합니다. 작은 입력에는 가장 작은 지원 단계인 1080p 값을 적용하고, 세로 영상은 가로·세로를 바꾼 같은 단계로 처리합니다.

| 해상도 | 30fps 이하 | 30fps 초과~60fps | 유튜브가 제시한 4K 범위 |
|---|---|---|---|
| 1080p 이하 | 8 Mbps | 12 Mbps | — |
| 1440p 이하 | 16 Mbps | 24 Mbps | — |
| 4K 이하 | 45 Mbps | 68 Mbps | 표준 35~45 / 고프레임레이트 53~68 Mbps |

- 프리셋의 오디오는 AAC-LC 48kHz이며 모노 128, 스테레오 384, 5.1은 512 kbps로 설정합니다. 이외의 채널 구성은 스테레오로 변환합니다. 일반 변환은 원본 오디오를 복사합니다.
- 일반 변환의 기본값은 HEVC NVENC, `p5`, VBR CQ 19입니다. H.264·HEVC·AV1, CQ 1~51, 목표 비트레이트를 선택할 수 있으며 품질과 비트레이트는 상호 배타적입니다. 0은 NVENC의 자동값이므로 품질 옵션으로 받지 않습니다. CQ 숫자는 코덱 간 같은 화질을 뜻하지 않으며, 실제 파일 비트레이트는 복잡도에 따라 목표보다 작을 수 있습니다. 설치된 FFmpeg의 각 `-h encoder=*_nvenc`에서 옵션을 확인했습니다.
- 명시한 코덱·품질·비트레이트가 프리셋보다 우선합니다. HEVC·AV1의 비트레이트는 H.264용 표와 같은 값을 사용하는 보수적인 프로그램 정책이며 코덱별 공식 권장값으로 간주하지 않습니다. H.264 10비트는 이 PC의 RTX 4080 SUPER에서 지원하지 않으므로 HEVC·AV1 사용을 안내합니다.
- 유튜브는 edit list가 없는 MP4를 권장하지만 AAC 지연 보정을 위해 FFmpeg 기본 동작을 유지합니다. `use_editlist=0`과 `negative_cts_offsets`를 사용한 1초 실험에서 영상 시작은 0초였지만 AAC 길이가 21.3ms 늘었습니다. 관련 옵션: [FFmpeg MP4 muxer](https://ffmpeg.org/ffmpeg-formats.html). 장시간·VFR 동기 검증은 P4-3의 범위입니다.
- 검증: 인코딩·CLI 테스트 55개 통과. 세 코덱의 CQ/VBR와 프리셋 덮어쓰기, 1080p/1440p/4K, 59.94fps, High 프로파일·B 프레임·GOP·Fast Start, 오디오 재표본화·복수 트랙·다운믹스를 확인했습니다. 실제 4K 샘플을 `--preset youtube --verify`로 변환한 `F:\Temp\FrameDoubler\out\FireEmblem_youtube_60fps.mp4`는 H.264 High/8비트/60fps, 영상 68.01 Mbps, AAC-LC 48kHz 스테레오입니다. 478프레임, 입력 대비 영상·오디오 길이 차이 각각 0ms, 잔여 중복 0.21%로 통과했습니다.
- 실제 샘플의 영상 길이는 7.966667초, 오디오는 7.914667초로 입력부터 52ms 차이가 있으며 출력도 이 길이를 유지합니다. 입력 영상 시작은 12.333ms, 입력 오디오와 출력 두 트랙 시작은 0ms입니다. `verify`의 길이 차이 0ms는 각 입력 트랙과 비교한 값이며, P4-3에서 시작 시각과 마지막 구간의 실제 동기를 별도로 확인해야 합니다.
